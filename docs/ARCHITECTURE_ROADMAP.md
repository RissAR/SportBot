# МЕТОДОЛОГІЯ ТА АРХІТЕКТУРНА ПОСЛІДОВНІСТЬ РОЗРОБКИ (Bot + Mini App)

Цей документ фіксує обов'язковий порядок проектування та розробки екосистеми Telegram Bot + Telegram Mini App (TMA). Мета — виключити хаотичні переходи між етапами («скакання з п'ятого на десяте») та гарантувати закладання критичних рішень на рівні фундаменту.

---

## 🗺 Послідовність фаз розробки

```
[ФАЗА 0: Каркас & Правила] 
          ↓
[ФАЗА 1: База Даних & Математика Слотів/Сутностей]

[ФАЗА 3: Telegram-бот (Навігація & Гібридні Сповіщення)]

          ↓

```

---

### 🔹 Фаза 0. Фундамент та архітектурні контракти
1. **Структура папок під Docker:**
   - `/data` — локальне сховище для SQLite (збереження між контейнерами).
   - `/backups` — щоденні автобекапи бази даних.
   - `/src` — бекенд (FastAPI, сервіси, моделі, бот).
   - `/frontend` — Telegram Mini App (React + Vite).
2. **Anti-Cache фундамент:**
   - Одразу у FastAPI реалізувати маршрутизацію `/app` із суворими антикеш-заголовками:
     `Cache-Control: no-cache, no-store, must-revalidate`, `Pragma: no-cache`, `Expires: 0`.
   - Версіонування URL у конфігурації: `get_webapp_url(v=1.0.0)` — запобігає «проблемі білого екрана» через агресивне кешування Telegram Webview.
3. **Спільний асинхронний запуск:**
   - Скелет `main.py` із запуском через `asyncio.gather(run_api(), run_bot())`.

---

### 🔹 Фаза 1. База даних та ядро бізнес-логіки
1. **Асинхронні моделі SQLAlchemy:**
   - Створення реляційної моделі (User, Service/Event, Resource/Master, Schedule, Appointment/Booking).
2. **Математика інтервалів на рівні БД:**
   - Накладання індексів.
   - Сувора перевірка перетинів часових інтервалів:
     `start_time < existing_end AND end_time > existing_start`.
3. **Сід-скрипт (`seed_initial_data`):**
   - Наповнення первинними тестовими даними для перевірки цілісності ще до запуску інтерфейсів.

---

### 🔹 Фаза 2. Безпечний REST API
1. **Криптографічна валідація Telegram `initData`:**
   - Реалізація валідації через HMAC-SHA256 (з секретним ключем, отриманим із `BOT_TOKEN`) одразу як FastAPI Dependency, а не в кінці.
2. **Захист від стану гонитви (Race Conditions):**
   - Бронювання/записи з використанням `asyncio.Lock` або атомарних транзакцій.
3. **Розподіл доступу (RBAC):**
   - Публічні ендпоінти: читання послуг, ресурсів, розкладу, доступних слотів.
   - Клієнтські ендпоінти: створення бронювання з валідацією телефону та імені.
   - Адмінські ендпоінти: захищені через `Depends(verify_admin)`.

---

### 🔹 Фаза 3. Telegram-бот (Навігація & Сповіщення)
1. **Клієнтський інтерфейс чату:**
   - Стартове привітання, перманентна Reply-кнопка меню.
   - Інлайн-каталог для користувачів, які воліють взаємодіяти без відкриття Mini App.
2. **Гібридне сповіщення адміна:**
   - При створенні бронювання через API — адмін отримує інформативну картку в боті з кнопками миттєвої дії («Підтвердити» / «Відхилити»).

---

### 🔹 Фаза 4. Telegram Mini App (Фронтенд)
1. **Стек:** Vite + React + Tailwind CSS.
2. **Дотримання Rules of Hooks:**
   - Оголошення хуків виключно на верхньому рівні компонентів (без умовних викликів або викликів після ранніх `return`).
3. **Клієнтський потік:**
   - Вибір напрямку / послуги -> вибір тренера / залу -> вибір дати і слоту -> модалка підтвердження контакту.
4. **Адмінський потік:**
   - Екран перегляду нових заявок, статусів та метрик.

---

### 🔹 Фаза 5. Автономність, Маркетинг, Дизайн-глибина & Деплой
1. **Фонові задачі (APScheduler / Celery / asyncio background tasks):**
   - Нагадування за 24 години та за 2 години до події.
2. **Маркетинг та утримання:**
   - NPS-опитування після події/тренування, повторні нагадування, генерація посилання в Google Календар.
3. **Дизайн-полішинг:**
   - Мікроградієнти, ефекти розмиття/скла, плавні анімації.
4. **Продакшен-деплой:**
   - Оптимізований мультистейдж `Dockerfile`.
   - `docker-compose.yml` (`restart: unless-stopped`, моніторинг логів, бекап бази даних у `/backups`).

## 💡 3 Головні інженерні закони

1. **Contract First (Спочатку контракти, потім кнопки):**
   Фронтенд розробляється лише тоді, коли зафіксовано схему даних у БД та формат API-відповідей (Pydantic-схеми).
2. **Hardening First, Polish Last (Спочатку залізобетонна надійність, потім краса):**
   Захист від подвійних кліків (Race Conditions), валідація `initData`, антикеш TMA та безпека адмінки закладаються в ядро. Градієнти та бліки накладаються в останню чергу.
3. **Decoupled Architecture (Розділення бізнес-логіки та візуального шару):**
   Логіка обробки даних не прив'язується до візуальних компонентів. Зміна теми чи переверстка інтерфейсу не повинна зачіпати API чи бізнес-правила.
